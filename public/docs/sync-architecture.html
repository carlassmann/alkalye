02 / follow one keystroke

Visible first, durable locally, then shared

  1. The editor produces a source edit. A native textarea owns input, selection and IME. A syntax overlay paints formatting. The source adapter maps prettified link positions back to Markdown positions.
  2. The session stages operations. Text inserts and removals refer to character identities. Other document values use registers. One document action can contain several operations, such as an asset manifest plus its Markdown reference.
  3. The local journal records the proposal. The optimistic view includes the edit immediately. "Saved locally" depends on successful durable persistence. A failed write keeps the unsaved draft available and prevents navigation from silently discarding it.
  4. Synchronization sends pending work. The session flushes drafts, publishes an offline creation if needed, pulls newer accepted actions, then submits pending actions in order. It pulls again after submissions. New asset chunks upload before the action that references them.
  5. The server accepts or refuses the action. It checks current authority, schemas, identities, text dependencies and relevant guards. Accepted facts, receipts and projections commit together in SQLite.
  6. Clients settle and merge. A client removes a pending action only when its exact identity is acknowledged. Other clients receive a notification and pull the accepted tail. Applying duplicate accepted facts does not repeat the edit.

The selected browser session debounces local-change synchronization by 500 ms. Online, focus, live connection and change notifications also wake it. A separate drainer can publish pending work in documents that are no longer selected.

03 / fast opening

Start with state, then catch up

A document you already have

Restore the accepted checkpoint and ordered pending actions from IndexedDB. Replay the local journal after the cache's covered position. Reapply pending work and render. Network synchronization can follow.

The cache is a rebuildable projection. A damaged cache can fall back to journal replay; the journal is the durable local evidence.

A document new to this device

Download a current server snapshot. It identifies the document, log and covered position, and contains a full CRDT checkpoint. It includes character identities, tombstones and causal information needed for later merges.

Fetching the whole historical event list is unnecessary for opening.

Snapshot through 120+Accepted tail 121, 122…+Pending local proposals

Old history is optional to download. The changes after your accepted position are necessary to become current. A checkpoint is more than a plain Markdown string: deleting merge identities from it would break offline reconciliation.

Three different kinds of ordering
Value What it means
Operation clock + actor identity Names contributions and gives replicas a deterministic ordering. It is not wall-clock time.
Server log position How far this client has consumed the accepted stream. Used for tail requests.
Local journal position How far the cached local projection has replayed proposals, receipts and other local facts. It is a different cursor.

The server saves durable checkpoints every 100 document versions. A cold server restores a checkpoint and replays its later accepted tail before returning current state. The browser receives the resulting snapshot.

04 / collaboration

Event sourcing records facts. The CRDT makes them merge.

Text has stable character identities

An insertion says which character it follows. A deletion names characters, rather than "delete position 17." Deleted characters remain available as anchors. Concurrent siblings have a deterministic identity order.

Two devices can insert at the same place offline and still agree once they receive the same accepted operations.

Other values have winning contributions

Comments, drawings, settings and manifests live in document records. Register writes choose a deterministic winner. Access writes and undo have additional validation; a text merge cannot grant someone permission.

Frontmatter is the metadata source. Its merge logic preserves concurrent key changes; sidebar titles and tags are derived copies.

src/shared/frontmatter-merge.ts
What belongs to a document's history?

Source, comments and replies, attachment references and manifests, whiteboard data, document themes and shared settings, and direct document grants. A multi-record action commits as one unit. Blob bytes are stored separately.

Workspace membership has its own facts because it governs many documents. Cursors, selections and presentation progress are transient presence messages.

How do cursors and comments differ?

Live presence broadcasts current source offsets for the caret and selection, plus display or presentation state where relevant. It is refreshed frequently and expires. Browser peer entries older than 10 seconds disappear.

Comment selections retain CRDT character anchors. Those anchors belong to durable document state and survive intervening source edits.

What changes when WebSockets stop working?

After three unhealthy socket attempts, the client switches to long polling. The default poll request can wait up to 20 seconds, returning early when a message arrives. Outbound watch and presence messages use a separate HTTP send request.

The same server participant logic checks access and broadcasts messages for both transports. While polling, the client probes WebSockets again after 90 seconds. Socket opening has a 10-second deadline; reconnect delays use capped exponential backoff with jitter.

Who decides access?

The server checks current workspace membership and direct document grants. Owners manage access; writers edit; readers read. The browser hides forbidden controls, but the server enforces the boundary.

A disconnected writer can still make a local draft using cached information. That draft has not been accepted remotely. If access was revoked, reconnecting cannot turn it into an authorized server action.

06 / undo, time machine and files

One history, several ways to use it

Undo appends a compensation

Undo targets a contribution. Text cancellation preserves peer insertions and overlapping peer deletions. Register compensation checks who still owns the affected value. Redo follows the compensation chain.

The server revalidates the compensation against current state and authority. Undo is not a replacement of everyone's current source with an old string.

Time machine reconstructs a past state

History loading is separate from ordinary opening. Reconstruct a selected point from a checkpoint at or before it, then replay the retained tail to that point.

Restoring content makes a new change in today's document. It does not reinstall historical permissions or delete later history.

Asset bytes have a separate lifetime

The browser stores verified Blob chunks in IndexedDB; the current Bun server stores chunks in SQLite. Actions and snapshots contain manifests and immutable references, not repeated video bytes.

Chunks must exist before acceptance of their referencing action. Old history and undo may still need bytes no longer referenced by current content.

Local files reuse the session

A chosen file or directory connects the document session to the File System Access API and file reconciliation. It does not invent another editor or CRDT.

The portable CLI also uses the shared session, with SQLite journals and the same HTTP document protocol.

What Effect supplies, and what Alkalye supplies

Effect supplies service construction through Context.Service and Layer, validated contracts through Schema, journals through EventLog, typed HTTP clients and APIs, SQL services and migrations, and concurrent work through scoped fibers.

Scope owns cancellation and cleanup. RcMap owns shared session or media leases. SubscriptionRef and Stream carry changing state. Queue, Semaphore and Schedule handle buffering, serialization and retry timing. Graph supports dependency and compensation planning.

Alkalye supplies the document model, CRDT and cancellation rules, permission policy, frontmatter semantics and product behavior. Platform adapters connect Effect services to IndexedDB, Web Locks, Web Crypto, DOM and Bun SQLite. Effect's event log does not automatically implement collaborative text merging.

Read in this order: editor input → shared session → journal adapter → HTTP transport → server acceptance → live notification → another session's merge. It is one write path with several adapters.

Observability without logging every edit

Effect spans follow document opening, synchronization and typed HTTP operations. Effect counters record outcomes, and histograms record latency. Labels describe operations and failure categories, never document text, account IDs or keys. Each client or server runtime owns its metrics registry.

Routine success updates metrics without logging. Slow operations produce rate-limited warnings; server storage outages and recovery produce transition messages. Settings includes aggregate client counts and timings in the diagnostic report. Client diagnostics stay local; no external telemetry exporter is configured.

08 / what the design does not promise

Important current boundaries

  • Document events are currently plaintext on the server. HTTPS protects transport. Account authentication uses recovery-key-derived identities; this is not end-to-end encryption of document content.
  • The live participant registry is in server memory. Restarting drops presence and connections; durable document state survives in SQLite. Multiple server instances would need shared notification routing and coordinated storage.
  • Bun and Cloudflare run the same document module. On Cloudflare, each workspace owns a SQLite Durable Object; attachments live in R2. A shared gateway handles authentication, routing and live notifications. Workspace partitioning distributes document storage, while those shared services remain a scaling boundary. Sockets currently use regular acceptance, without hibernation.
  • History retention and blob cleanup need a complete policy. Pruning must preserve reconstruction tails, undo needs and offline references. Permanent historical redaction is not implemented.
  • Some rejected-action recovery is automatic, some is still unfinished. Definite safe rejection can be recorded and withdrawn. Network failure is not proof of rejection; it keeps pending work. Inserted-text dependency closures are preserved for recovery. The recovery UI offers copying, export and retry; it does not automatically rebase rejected work or recover uncached attachments.
  • Fast opening still has a state cost. A checkpoint retains merge identities and tombstones. Its size can grow, and cold offline undo may scan retained local history. Snapshot and history separation removes mandatory old-history downloads, not every performance cost.

The latest completed verification covered 428 Bun tests and all 37 browser suites, including targeted reruns after test-harness fixes. Tests exercise real storage, permission changes, offline reloads, concurrent sessions, assets, undo and live transport fallback. They do not establish a production-scale latency or storage benchmark.

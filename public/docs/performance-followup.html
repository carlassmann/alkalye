7 October 2026. These narrow experiments follow the comparison with main. They compare rewrite revisions or implementation paths; main was not rerun here.

8 October: mobile taps and cached switching

Mobile pointer handling was expanding and aligning a document that was already fully rendered. It mixed estimated block positions with measured text geometry, moving the page after a tap. The handler now preserves the existing native input and drag lifecycle in that case.

The mobile run used actual coarse-pointer emulation at 393px with a 128KiB document, frozen assets and exact saved-content checks. Typing remained roughly 16–24ms; the first frame opportunity after tapping also remained much slower than the pointer handler. Commit 74bd83e fixes the tap bug, not the whole mobile frame budget.

Cached switching compares frozen 1bbe9da with only the accepted-source warm-up in 10b9ab7. A background snapshot now materializes accepted text before publishing the passive cache. Pending local edits remain separate. Public integration checks cover overlapping sessions, interrupted saving, retry and accepted versus pending content.

Three ordered browser trials per size and version used CPU tracing. Each trial accepted an edit and undo, then waited for the actual stored snapshot cursor before switching. A trial overlapping another test was discarded. These small samples show a useful improvement, not statistical certainty. Native Map cloning was also rejected: copying 1,048,576 entries took roughly 43ms in one task, with almost no total-time gain over cooperative copying.

A paired 1MiB CPU trace confirms that source and visibility traversal disappear from switching after warm-up. Map-copy samples remain roughly 294–299ms. The largest main-thread task was 10.5ms before and 11.4ms after; faster readiness does not establish an 8.33ms frame budget.

8 October: prepare collaborative batches once

A delayed IndexedDB callback resumed CRDT validation and application. The old path prepared each replica during validation, then prepared it again during application. The new batch operation prepares every replica once and commits only after all preparations succeed. Public contracts cover a conflict in the last replica, duplicate participants, concurrent text and frontmatter, replay, causal undo and independent fork histories.

Undo copies state cooperatively

Action staging now uses a detached, cooperative replica fork instead of encoding and restoring the entire checkpoint. In three matched browser trials per version, undo in a 1 MiB document reached two paint opportunities in 626.6 ms median, down from 1,259.8 ms. The largest main-thread task fell from 853.7 to 290.3 ms; the fully accepted checkpoint took 2,605.1 ms, down from 3,008.3 ms.

Both clients used the same native server and restored identical disposable data and browser profiles. All six trials passed exact source, trusted undo, strictly newer accepted-checkpoint and zero pending/rejected-action checks. Loaded chunk URLs and decoded sizes matched expected builds; loaded bytes were not cryptographically verified. These tasks still exceed 8.33 ms. Samples and method: experiments/performance/undo-fork/.

A separate three-trial comparison then skipped source materialization when text undo has no register restoration. Median time to two paint opportunities fell from 672.0 to 545.6 ms; the accepted checkpoint fell from 2,659.6 to 2,241.4 ms. The largest task remained slow: 316.1 versus 332.3 ms. All six exact-source and accepted-state checks passed. This improves undo latency, not the frame budget. Samples: experiments/performance/undo-fork/empty-inverse-results.json.

Body edits remain incremental after metadata changes

Merged frontmatter can leave raw and canonical atom arrays with different lengths. The old cache rejected those arrays, rebuilding the whole source after each keystroke. The fix maps body splices between the arrays and verifies their anchors. Header-boundary mismatches still use the full projection.

Changes kept and rejected

Deletion-history removal and cancellation sets now use copy-on-write: forks share read-only sets, while edits replace only touched sets. Independent undo and partially interrupted copies remain isolated. In a fully deleted 128KiB public Replica probe, native Bun fork median fell from 13.39ms to 0.47ms; cooperative copying on Bun fell from 16.60ms to 11.01ms. These three-sample module measurements do not establish browser loading performance or gains for clean histories.

Library synchronization now skips a second save after a successful, clean synchronization. Real IndexedDB and authenticated HTTP tests cover offline reloads, revoked access, retries, and interruption during concurrent edits. One redundant summary projection attempt disappears; actual changed writes and network pulls remain the same.

Accepted-cache replicas remain isolated between overlapping sessions. Direct reuse failed the public integration checks. An Effect HashMap prototype made copies cheaper but lookups and scans much slower than native Map in Bun. Neither unsafe cache reuse nor that map replacement entered production.

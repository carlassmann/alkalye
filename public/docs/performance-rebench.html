Where the rewrite remains inferior

  • Large preview rendering: 128 KiB rich Markdown takes about 7.3 times as long. Both previews were checked for the correct title and exactly 1,297 reference links; this is a real readiness regression.
  • Some rich-document edits: 32 KiB beginning / middle edits take 30–31 ms versus 24–25 ms on main. Rewrite animation-frame callbacks consume roughly 18–20 ms, versus less than 1 ms on main. That exceeds an 8.3 ms frame budget before browser painting. Wrapping refinement and geometry refresh are candidates; no CPU trace confirmed the cause.
  • Find: finding the reference matches in 128 KiB takes 31.1 ms versus 24.1 ms. The rewrite gate checks both match count and a visible highlight.
  • Input blocking: the 128 KiB single-character synchronous input span is about 6.4 ms versus 0.8 ms. Main defers work, so this measures blocking at the event boundary, not equivalent total application work. The rewrite reaches its next verified frame opportunity slightly earlier: 21.8 versus 25.3 ms.
  • Reconnect: after a verified offline interval, the rewrite's peer catches up in 84.5 ms versus 41.3 ms on main. Three samples make this indicative; it is not a stable percentile estimate.

What improved

At 128 KiB, warm reload fell from 406 to 298 ms and end-of-document chunk input from 26.8 to 11.4 ms. The 2 KiB preview improved from 58.5 to 33 ms. Passive peer updates fell from 300 to 86.5 ms with each app's defaults. Main debounces ordinary document saving by 250 ms; this is an application scheduling comparison, not proof that the underlying transport is 3.5 times faster.

Replacing around 1,300 selections took 54 ms in the rewrite versus 97 ms on main. Selection setup was excluded; main used its public EditorSelection API, the rewrite its shortcut. One baseline match had been modified by a discarded shortcut attempt, so counts were 1,297 versus 1,298. Three samples are indicative.

Extreme cases and remaining gaps

A 1 MiB long-paragraph fixture could not be prepared within the harness deadline; both attempts were aborted. Setup is excluded from load timings. This establishes a benchmark gap, not an application failure or a valid comparative 1 MiB latency. There is no new CPU-throttled mobile, history-heavy document or forced-polling browser comparison.

Programmatic scrolling produced a 16.7 ms median frame interval in both versions. No difference was detectable at the browser's 60 Hz cadence. This cannot certify 120 Hz presentation or physical wheel / fling behavior.

The rewrite's first selection of an existing 128 KiB document took 300 ms; eight later selections had a 152 ms median. The main switch batch was interrupted for other implementation validation, so it has no valid comparative number.

24 writers through real storage and transport

A separate rewrite integration journey passed 1,267 assertions with 24 writers, mixed WebSocket / polling transport, durable SQLite storage, presence and offline recovery. Eight rounds produced 192 operations on an 8 KiB document. Commit median was 258 ms, p95 508 ms, maximum 574 ms; complete journey throughput was 24.9 operations per second. Clients, server, synchronization barriers and assertions share one process. This is not isolated server capacity or browser frame performance.

Measurement limits

  • Reload runs from navigation start until the content-known editor is ready and a frame opportunity occurs. Both PWAs are controlled by their service workers. One extra warmup precedes nine samples.
  • Input, find, preview and switching run from a trusted event to verified source / UI state plus later animation-frame opportunities. Automation roundtrips are excluded. This does not measure completed pixel presentation and may miss deferred work.
  • CDP insertText omits keydown. Chunk input inserts approximately 10–17 characters per event; single-character results are separate.
  • Peer timestamps use performance.timeOrigin + performance.now() on the same host. Passive consumers use cloned disposable profiles and never produce text operations. Reconnect requires 750 ms without peer receipt before network restoration. WebSockets are preferred by default; forced polling was not benchmarked.
  • Fixture-size batches are interleaved by version, not randomized per keystroke. Other apps were open; parallel builds and test suites were paused for timed samples. Small differences and all three-sample cells need another run.
  • The machine is an Apple M5 Pro MacBook Pro with 18 CPU cores and 64 GB RAM, macOS 27.0.1, Headless Chrome 154.0.8037.58, 1280×900 viewport. No CPU throttling or artificial network latency.

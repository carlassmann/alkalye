**What I verified**
- **Constructor fix:** `crdt-candidate.ts:2420` now calls `new PagedChildrenIndex(...)` correctly.
- **Copy-on-write, both sides:**
  - Forking a small index marks parent and child as not owning the shared map, and the first write on either side copies it.
  - Forking a large index resets the parent's ownership and gives the child no ownership.
  - Promotion only reads the shared map, so a sibling that hasn't promoted stays intact.
  - Grandchildren share the same map and all start without ownership. Correct, at the cost of extra copies.
- **Order after promotion:**
  - The map keeps first-insertion order, so promoted ordinals are 0..4095 and the new key gets 4096.
  - Updating an existing key never moves it, in either form.
  - So `values()` order, and therefore checkpoint and durable bytes (`crdt-candidate.ts:1875`), match the control.
- **Promotion is safe:** it doesn't yield, call back or throw part-way, and it only swaps `large`/`small` after the loop. No partially built index can leak.
- **Interrupted cooperative fork** (`crdt-candidate.ts:181`): the parent can be left marked as not owning targets it already visited. That costs one extra copy and nothing else, and the existing tests for concurrent edits rejecting partial copies still cover it.
- **Open iterator during checkpoint writes:** behaves the same as the control. Not a regression.
- **Tests:** the post-promotion fork test (8193 chars, edits to the old page, child, grandchild and sibling) closes the gap from the earlier review.

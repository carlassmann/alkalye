## Correctness (`runtime/src/shared/model.ts:346-415` vs `baseline/src/shared/model.ts:346-382`)
- **Merge decision:** the merge condition is the same. `length` tracks exactly what `previous.value.length` was in the baseline, and it resets in `finishRun` before the next run starts. The lone-surrogate test still runs on the raw atoms.
- **Fast paths:** `finishRun` returns `pieces[0]` when nothing has been flushed yet. `pieces` can't be empty at that point, because `append` always runs before it. The output strings are the same as `+=` for string values.
- **Stale value mid-run:** while a run is still open, `previous.value` holds only the first piece. Nothing reads it inside the loop or across a yield, and `insert` doesn't escape until the return. Interrupting the generator leaves no partial result.
- **Callers:** `checkpoint.ts:169` (cooperative) and `compactOperation` (non-cooperative) both work unchanged. `CompactAtomSchema` (`checkpoint.ts:129`, at most 2M characters) is still satisfied.
- **Your copies:** `runtime/`, `model.ts` and `tested-candidate-model.ts` contain the same compaction code. I compared the key lines, not a full diff.
- **Not blockers for this change:**
  - The lone-surrogate server/session insert failure happens identically in both arms. Track it separately.
  - A `value` that isn't a string would come out differently. Schemas stop this from reaching the code.

## Caveats in the raw data
1. **The `mc1m` measurements are confounded.** All 3 baseline runs ended with the badge showing `pending: "1"`; all 3 candidate runs ended with `"0"` (`allocation-results.json:2397,3575,3958`). A save may still have been in flight while the baseline window was measured, so the `mc1m` busy-union and largest-task differences can't be credited to the candidate.
2. **`eventTiming` doesn't support a comparison.**
   - The set of recorded entries differs from trial to trial.
   - Candidate `long1m` trials 1 and 2 show keydown/keypress at 24 ms; every baseline shows 16 (`:802,809,2000,2007`). Processing time is about the same, and the values are rounded to 8 ms, so this is weak evidence against the candidate, not a finding.
3. **The `frames` arrays don't agree with the traces.** No frame in any of the 12 runs reaches 18 ms, yet the traces show tasks of 20 ms and more. Don't use the frames as jank evidence. Everything here assumes a 60 Hz display, and nothing in it supports a 120fps claim.
4. **The mechanism is unidentified.** The largest tasks are `o.port1.onmessage` and `app.js:1653`, not compaction itself. The busy-union reduction is real at n=3, but nothing in this data shows why it happens.
5. **Untested paths:**
   - **Fragmented input:** many short runs from multicursor edits, interleaved actors or undo-heavy histories. `mc1m` doesn't exercise this. It's the candidate's worst case, because every run adds a push and a reset on top of the baseline's spread.
   - **One 2M-character run in cooperative mode:** the final join happens all at once between yields.

## Recommendation
- **Adopt once:**
  - the `mc1m` pending-save asymmetry is explained, by re-reading the saved traces or by waiting until pending is 0 before measuring;
  - a fragmented-atom case shows no regression. The deep checkpoint suite or a module test can cover this, so no new browser benchmark is needed.
- **If you must decide now:** adopting is low-risk. It changes no behaviour, is easy to revert, and shows no regression above noise. Scope the rationale strictly to "fewer >8.33 ms tasks and lower busy union on `long1m`, n=3". Don't claim it improves Undo's worst-case task, input latency, heap or GC.

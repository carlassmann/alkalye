No blockers to correctness. As long as atom IDs in `next` are unique, the candidate gives exactly the same result as the baseline for every input. The open problems are about measurement.

**Correctness (checked against baseline `mapSelectionBoundariesFallback`)**
- **Anchor survives:** same formula, `start + min(inside, len)`.
- **Anchor missing:** the baseline's `predecessor` is the end of the last *previous-order* atom that survived. That includes empty atoms, because `if (mapped) predecessor = mapped.end` runs for them too. So when the immediate predecessor survived, its `.end` is exactly what the baseline returns. This holds however `next` is reordered, because both versions walk the previous order. Remote RGA moves and frontmatter `sourceAtoms` key reordering give the same result in both, including the same odd placement when a moved predecessor's end lands somewhere else.
- **First anchor missing:** returns 0 in both.
- **Fallback:** called with the original `offsets` and the partial result is thrown away, so it is exact.
- **UTF-16:** `inside` is in code units. Landing mid-surrogate gives the same result as the baseline. Negative or out-of-range offsets also behave like the baseline. One exception: the `previous === next` shortcut returns out-of-range offsets unchanged where the baseline drops them. That is unreachable after the `end <= length` check, and probably never true anyway, since the fork has its own `sourceCache`.
- **Duplicate IDs (only theoretical difference):** the baseline's `nextPositions` keeps the last occurrence. The candidate stops early once `positions.size === wanted.size`, so it may keep the first. `rawVisible` comes from a tree and `sourceAtoms` only reorders or filters raw atoms, so duplicates look unreachable. The `literalAtoms` with `id: ""` exist only in `inverseHeader` and get fresh IDs on insert (`crdt.ts:1334`).

**Performance traps**
- **Fallback is not rare.** Remote deletion of a run of 2 or more atoms around the caret, or Undo reinserting with new aliased IDs (`crdt.ts:1353`), means anchor and predecessor are both gone. That costs the prefix scan, plus a full `next` scan (no early stop, because the IDs are missing), plus the whole baseline. Worst case is about 2× the baseline.
- **Fallback is all or nothing.** With 512 ranges (about 1,026 offsets), one anchor falling back reruns everything.
- **Early stop rarely fires.** Any missing wanted ID forces a full `next` scan, and every missing anchor adds its predecessor to `wanted`. The real gain is only skipping n `Map.set` calls and object allocations.

**What to fix before the native matched 1/512 Merge + acceptedUndo lease**
1. **The native arm still runs the baseline.** `native-runtime/src/client/worker-document/worker-editor-basis.ts:493` has the old `mapSelectionBoundaries`. The candidate exists only in `runtime/`, so the native lease would measure the baseline.
2. **The policy mark is mislabelled.** The candidate still emits `performance.mark("mapping-policy:original")` (line 342, also space-indented), so traces can't tell the arms apart.
3. **Nothing records which branch ran.** Add per-call counters for anchor-hit, predecessor-hit, first-0 and fallback. The gates (`worker-rpc-gates.ts:43,56,87`) check results, not paths: line 43 is named "through original fallback" but the candidate probably answers it via predecessor-hit. Without counters, a 512/acceptedUndo timing may be measuring the fallback path, which is slower than the baseline.
4. **Missing cases:**
   - Anchor missing with a surviving *empty* immediate predecessor. This can't be reached now, since empty-atom creation fails earlier; record it as a coverage limit.
   - Undo aliasing where the predecessor is aliased but the anchor isn't.
   - Within one 512-range call, a mix of anchors that resolve directly and one that falls back.
   - A frontmatter key reorder where the predecessor moved, to show it still matches the baseline.
5. **Optional guard against the duplicate-ID difference:** in debug builds, assert that the `next` IDs are unique, or drop the early stop. Either removes the only route to a different result.

No timing claims are possible yet. Let the branch counters decide whether the fast path is what gets measured.
